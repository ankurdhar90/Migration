Signatures: how memory knows two issues are the same problem

Two engineers can describe the same bug in completely different words. Comparex cannot: it reports the same structure every time. Memory turns that structure into a fingerprint, at three levels of strictness.

What goes into each level

L1 finds the exact repeat

The same column on the same tables, with the same types, fails in the same way again. The strongest match: whatever fixed it last time is very likely to fix it now.

L2 carries lessons across tables

Table names are left out on purpose. Any SQL Server datetime that lost sub-second digits in Snowflake looks the same, so a fix proven on orders helps on invoices too.

L3 brings up table history

Only the tables and column. Even if the problem is new, past issues on this table can carry warnings (“the audit job reads this column”).

And L4? When nothing matches structurally, memory falls back to text similarity over the issue titles and notes (TF-IDF plus LSA, a classic technique with no model involved). It counts the least: weight 0.3 times the similarity.

The value pattern is the secret ingredient

“Values don't match” is too vague to learn from. What matters is how they differ. Memory looks at the sample value pairs in the compare result, runs a list of simple rules in order, and keeps the name of the first rule that fits at least 60% of the samples. Then it throws the samples away.
