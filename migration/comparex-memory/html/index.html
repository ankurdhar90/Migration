Start here

Comparex keeps finding the same problems. Memory lets the agents remember how they were fixed.

Today, every difference Comparex reports is triaged and fixed from scratch, even when the same kind of problem was solved last month on another table. The memory layer watches what the pipeline already produces and hands the agents a short history note for each new issue.

The whole system in one picture

1

Nothing upstream changes

The top row is how work happens today. Memory only reads its files and git history. If memory is switched off, the pipeline behaves exactly the same.

2

Memory learns by watching

Each time new files appear, the ingester turns them into rows in a local SQLite database. Nobody has to write anything extra.

3

Comparex is the judge

A fix only counts as working when the next Comparex run no longer shows the difference. What an agent claims in a handoff does not count.

4

Agents get a note, not orders

For each issue, memory writes one Markdown file. Triage and Amp read it as advice; current Comparex results always win.

Three ideas carry the whole design

Matching

Same problem means same structure

Two issues are "the same" when Comparex describes them the same way: engine pair, kind of difference, type families, and the pattern in the values. Text search is only the last resort.

Try the signature lab →
Trust

Evidence, not opinions

Every fix is checked against the next compare run and scored. Repeated wins turn a fix into a playbook; failures and caveats are remembered too.

Play with the confidence score →
Safety

Deterministic and model-free

No LLM runs inside memory. It is Python and SQL: the same inputs always give the same database rows and the same memory file, byte for byte.

Rules it never breaks

These come from the problem itself, so they hold in every phase and both versions. If a design choice breaks one of them, the choice is wrong.

  • It never edits an issue, triage or handoff file, an agent prompt, or Comparex itself.
  • It never writes outside its own folder, .memory/ (plus the Snowflake memory schema in version 2). One guard function enforces this, and a test proves it.
  • It never stores real data values from the tables. Sample values are looked at once to name the pattern, then thrown away.
  • It never calls an LLM or a hosted model.
  • It never makes a claim without a source. Every recommendation cites an issue ID or commit.

Words you will see

TermPlain meaning
Compare runOne time Comparex compared a source table with a target table, plus the list of differences it found.
DifferenceOne finding at column level, for example "values in created_at do not match on 1,200 rows".
IssueOne problem, written as an issue MD file with an ID like ISSUE-123.
SignatureA fingerprint of a difference, stored at three levels (L1, L2, L3) as short hashes.
ResolutionOne attempt to fix an issue, usually one or more git commits plus the handoff file.
OutcomeWhat the next compare run said about that attempt: pass, partial, fail, or unverified.
Approach keyA short label for how something was fixed, like config_change:datetime_precision, so similar fixes group together.
PlaybookA fix that has passed often enough on the same kind of problem to be recommended.
ObservationA caveat attached to a fix: info, warning or blocker.
