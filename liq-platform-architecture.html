Where the platform boundary sits

This is a platform migration, and the tier-1 cutover moves the boundary to just after tier-1. The SnowIn_* tables and the alias are the bridge across it.

Reconcile at four levels, not three

Both platforms build their own CDM from the sources. A tier-1 break can come from a CDM difference upstream, so compare CDM first. That tells you whether a break is a data lineage problem or a tier-1 logic problem.

Questions this view raises

1

Same snapshot of sources?

Do both platforms pick up the same file or extract for a business date? If not, level-1 breaks are timing, not defects, and the data gate has to check source completeness on both sides.

2

Keys with Snowflake as the end state

Translating Snowflake keys into SQL Server's key space builds a mapping you unwind when downstream moves. Generating keys on load in tier-1, or seeding Snowflake from SQL Server's key ranges, survives both phases. Where are keys generated today?

3

What is the DMNA tool?

Is it in-house or third party, and does Control-M schedule it? Its completion is the in-condition for the data gate.

4

How long can legacy CDM stay fed?

Rollback depends on the SQL Server chain running daily. If other consumers leave CDM, or the CDM team plans to decommission it, the rollback window has a hard end date.

5

Bridge or permanent?

If downstream follows, the thin procs and SnowIn_* are scaffolding. Keep them simple and avoid building logic into them that a later phase has to move again.
