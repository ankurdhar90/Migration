LIQ migration · recommended go-live · v3

The best match for LIQ

The plan for one table, Transaction.TBLDeposits, repeated for every tier-1 table. Snowflake data takes over the tier-1 interface tables by rename. Everything after tier-1 stays on SQL Server, unchanged. The rename is proven in UAT against production's numbers before it touches production.

  • Only tier-1 changes. Deposit enrichment, the other tier-2 processes and the reports aren't touched.
  • Same names, real tables. Tier-2 keeps reading Transaction.TBLDeposits. No synonyms.
  • One table at a time. Every step is defined for a single table, then repeated.
  • UAT is the parallel run. UAT is production-like with the same sources, is compared with production's numbers, and has no other environment.
  • Liquidity itself stays on SQL Server. A parallel Liquidity database comes in a later phase.

The switch, for one table

Flip between before and after the rename. Tier-2 always reads Transaction.TBLDeposits. Only what sits behind that name changes.

Production is the baseline, UAT is the proof

Both environments get the same source data at the same cut-off. UAT runs tier-1 from Snowflake, and production runs the legacy path. The numbers are compared every business date at three levels.

The path for one table

Drawn the same way as the case playbooks. UAT runs side by side with production until the production rename, and the legacy table stays loaded as a backup after it.

The rename for one table

Two schema moves in one transaction. The Snowflake-fed table takes the original name, and the legacy table moves aside and keeps loading as the backup. The steps are identical in UAT and production.

Runbook script for one table: UAT first, then production

-- 1. PREPARE (before the window)
--    empty the SnowIn table, copy all legacy history with its original identity values
TRUNCATE TABLE SnowInTransactions.TBLDeposits;
SET IDENTITY_INSERT SnowInTransactions.TBLDeposits ON;
INSERT INTO SnowInTransactions.TBLDeposits (<all columns>)
SELECT <all columns> FROM Transaction.TBLDeposits;            -- up to the previous business date
SET IDENTITY_INSERT SnowInTransactions.TBLDeposits OFF;
DBCC CHECKIDENT ('SnowInTransactions.TBLDeposits', RESEED, @max_legacy_id);  -- new IDs above old max

-- 2. RENAME (quiet window, nothing reading the schemas)
BEGIN TRAN;
  ALTER SCHEMA LegacyTransactions TRANSFER Transaction.TBLDeposits;
  ALTER SCHEMA Transaction        TRANSFER SnowInTransactions.TBLDeposits;
COMMIT;
-- reapply grants on both tables (a schema transfer drops them)

-- 3. REPOINT DAILY LOADS
--    DMVA target           -> Transaction.TBLDeposits
--    SSIS delete + destination -> LegacyTransactions.TBLDeposits (config change)

-- ROLLBACK
BEGIN TRAN;
  ALTER SCHEMA SnowInTransactions TRANSFER Transaction.TBLDeposits;
  ALTER SCHEMA Transaction        TRANSFER LegacyTransactions.TBLDeposits;
COMMIT;
-- reapply grants; DMVA -> SnowInTransactions, SSIS -> Transaction

Why the SnowIn table is emptied first: the rows DMVA has already loaded got identity values inside the SnowIn table, and those can clash with legacy IDs. Copy legacy history first, reset the identity, then let DMVA load from the first test date. From then on, every new ID is above the legacy maximum.

Stage by stage

Gate numbers are suggestions for SteerCo to agree.

1

UAT shadow (running now)

Legacy SSIS loads Transaction.TBLDeposits, and DMVA loads SnowInTransactions.TBLDeposits. The three-way reconciliation proves Snowflake matches legacy at tier-1.

Exit
At least 20 clean business days including a month-end, structure pre-checks passed
Way back
Nothing has changed
2

UAT rename and interim testing

Prepare, rename and repoint in UAT. Tier-2 then runs unchanged on Snowflake data every day and is compared with production at tier-1, tier-2 output and report level. Rehearse the rollback and the rename again, both timed.

Exit · G1
At least 20 clean business days including a month-end and a quarter-end, zero unexplained breaks, report owners signed off, rollback timed
Way back
Rename back in UAT. Production isn't affected.
3

Production rename

The same runbook in production for this table, in a quiet window. From the first business date on, Transaction.TBLDeposits (Snowflake) is compared daily with LegacyTransactions.TBLDeposits (legacy backup).

Before
G1 passed for this table, decision owner signed off, window booked
Way back
Rename back. Seconds, with the backup already current.
4

Soak, then decommission

SSIS keeps loading the backup through at least one month-end. Then take a cold backup, stop the SSIS job and LIQ proc for this table, and drop LegacyTransactions.TBLDeposits after a read-only period.

Exit · G2
Clean soak, sign-off, no other users of the legacy table or proc
Way back
None once SSIS stops. This is the point of no return.

The earlier alias-based in-and-out step isn't needed in this plan. UAT gives a full parallel run against production, so the go-live goes straight to the rename.

How the way back changes

Config: one master at a time

1Never edit both sidesUntil a Config table is renamed, SQL Server is the master and Snowflake gets a copy.
2The master moves with the renameWhen a Config table is renamed in production, Snowflake becomes its master and edits in SQL Server stop.
3Freeze around each renameNo changes to that table for a few business days either side.
4Reconcile dailyBy business key and code, so drift is caught within a day.

Table order and groups

Which tables go first, and which have to move together because tier-2 joins them, such as Transaction with the Reference tables it uses?

2

Two loads per table

Can SSIS keep loading the legacy backup alongside DMVA through the soak? Snowflake landing early helps.

Comparing UAT with production

Can the reconciliation tool read both environments, or do production's numbers need copying into UAT?

Tolerances and owner
