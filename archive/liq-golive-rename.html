LIQ migration · go-live option B

Rename the tables, retire SSIS

At go-live, the SnowIn_* tables take the place of the tier-1 Transactional, Reference and Config tables. LIQ tier-2 and the enrichment modules read the same table names as before, and SSIS no longer loads tier-1.

  • Legacy SQL Server route
  • Snowflake route
  • Retired at go-live
  • X stands for every tier-1 table, and the same applies to Reference and Config

The rename, step by step

Move whole tables between schemas instead of renaming them inside one. Each table keeps its own name, the old one is kept for rollback, and the change is metadata only. Run every table in one transaction.

Follows the namekeeps working

  • Tier-2 procs and views that select from Transactional.X
  • Synonyms and dynamic SQL
  • Ad hoc queries and report datasets

Follows the objectgoes to Legacy.X

  • Permissions granted on the table
  • Foreign keys that point at it
  • Schema-bound and indexed views
  • Triggers, CDC, change tracking and replication
  • Indexes, unless SnowIn.X was built with the same ones

The history problem

Tier-1 keeps history, and you've confirmed it must stay that way. SnowIn_* holds only the latest business date, so after a straight swap tier-2 lookbacks find one day of data. The history goes into Legacy.X with the old table.

The daily load after go-live

Without SSIS, the landing tool's write is the tier-1 load. If it writes straight into the live table, tier-2 can read a half-loaded date and the data gate runs too late to stop it. Landing into a staging table and then publishing keeps the gate in front.

Questions to settle

1

Once, or every day?

A daily swap can't keep history unless SnowIn.X holds all of it. Is the rename a one-off at go-live, with daily writes afterwards?

2

Why rename instead of publish?

A small T-SQL publish proc into the existing tables also removes SSIS. It keeps history, grants, FKs and indexes, and rollback is just re-enabling SSIS. What does the rename give you that publish doesn't?

3

Who owns Config?

If people maintain config rows in SQL Server today, a Snowflake-built table renamed over the top would overwrite their edits.

4

What binds to the object?

Inventory FKs, schema-bound views, triggers, CDC and grants on every tier-1 table before choosing. Each one has to be recreated at go-live and again on rollback.

5

Keys with no layer in between

No proc sits between Snowflake and tier-1 any more, so the surrogate keys have to be right in Snowflake. Seeding Snowflake from SQL Server's key ranges becomes close to mandatory.

6

Can tier-2 read mid-load?

Check the isolation level on the LIQUIDITY database, and whether any tier-2 job could start before the load finishes.
